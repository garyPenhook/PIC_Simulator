# Review findings (2026-11-11)

Review of picsim 0.2.9 (commit `343848f`): the simulator library, `basil-sim`, `pic-sim`, the tests and the docs.
It follows `REVIEW-FINDINGS.md` (2026-11-05), which covered the device descriptions; those are not re-audited here.

Nothing in the source was changed. Each finding says how it was established:

* **T** = reproduced by running it (a throw-away test or the command shown).
* **R** = found by reading the code; not run.

Priority: **H** crashes or gives wrong results in ordinary use; **M** wrong or misleading in a narrower case; **L** minor.

## Summary

| | Count | Worst |
|---|---|---|
| Simulator bugs | 17 | B1: a write to `T4TMR` crashes the simulator on the PIC18F27Q10; B9: a warm reset erases the PIC18 data EEPROM |
| Command line (`basil-sim`) and stimulus | 11 | C1: `--dump NAME:<large>` aborts with an allocation failure |
| Window (`pic-sim`) | 9 | G1: the stimulus file's `fosc_mhz` is overwritten every frame |
| Performance | 6 | P1: the PIC18 core runs at about 20% of real time for a 64 MHz part |
| Tests and tooling | 7 | Q1: `cargo clippy --all-targets` fails |
| Documentation | 8 | D1: the PDF manual is for 0.2.4 |

State of the tree: `cargo build` is clean, `cargo test --workspace --release` passes (all suites, 0 failed),
`cargo clippy --workspace --all-targets` stops on one error, `cargo fmt --check` reports 1117 differences.

## Method

1. Build, test, clippy and rustfmt over the workspace.
2. Every Rust source file was read: both cores (`pic18.rs`, `pic16.rs`), `periph.rs` and the nineteen files under
   `periph/`, `mem.rs`, `machine.rs`, `machine16.rs`, `hex.rs`, `config.rs`, `pace.rs`, `stimulus.rs`, `lines.rs`,
   `disasm.rs`, `devdesc`, and both front ends. `debuginfo.rs` was read for its loader and frame logic; its type
   formatting (lines 536-900) was skimmed. The shell and Python scripts were read.
3. Every device file loaded, validated (`Device::validate`) and bound to a machine; hook codes checked for duplicates.
4. Fuzzing of `basil-sim` (release build): 1600 corrupted ELF files, 3000 hex files with corrupted bytes on six parts,
   1050 random programs on seven parts. Then 120 random programs on each of eight parts with the debug build
   (arithmetic overflow checks on).
5. Edge-case command lines by hand.

Fuzz result: the ELF reader and the PIC16 core gave no crash and no hang. The PIC18 side gave one crash class (B1) and
time-outs that come from P2.

### B1/B2: suggested fix

The hook codes are hand-allocated `u8` ranges and the space is nearly full (QUART ends at 157 where the WDT codes begin,
SPI ends at 184 where the comparators begin). Either move `NVMQ0` or the Timer4/6 base, or replace the `u8` with an
enum so the compiler keeps them apart. A test that binds every device and asserts that no two addresses share a code
catches this class; the probe used for this review found it on six parts in under two seconds.

## Window: `pic-sim`

No thread other than the UI thread touches the machine, so there is no data race to find. The controls that stay
enabled while a run or a step job is active were each checked: *Load*, *Reset* and *Pause* clear `running` and `job`
first; *Run*, *Step*, *Step over*, *Line*, *Line over* and *Out* are disabled; a dropped `.hex` is ignored while
running. The remaining problems:

## Performance

Measured with the release build on this machine; `xc8_o1_q10.hex` and `xc8_o1_p16.hex` are busy loops.

| ID | Pri | How | Finding |
|---|---|---|---|
| P1 | M | T | PIC18: 200 M cycles in 60.6 s = **3.3 M cycles/s**. PIC16: 200 M cycles in 20.8 s = **9.6 M cycles/s**. Real time for a 64 MHz part is 16 M cycles/s, so "1x (real time)" cannot be held for a PIC18 at 64 MHz, and the window's "% of real time" will show about 20%. Not profiled (`perf` is not installed). From reading, the cost per instruction is in `Periph::sync`: it runs every model after every instruction and `sync_core` builds seven `Vec`s each time (`ev`, `comps`, `hits`, `periods`, `t1_run`, `late`, `t1_prep`), `ioc_scan` builds another. Skipping `sync` until the next cycle at which any model has something due is the usual cure; the PIC16 core's per-register sync is the evidence that it pays. **Fixed** (`d30a10e`, `bfc039c`, `59d93ba`): `sync_core` reuses its buffers, and a run (`Machine::run`, `Machine16::run`) skips the end-of-instruction sync until the next cycle at which a model has something due; register accesses catch the models up first. `PICSIM_CHECK_LAZY=1` checks every skip against a full sync. Same benchmarks after: PIC18 200 M cycles in 4.0 s = **50 M cycles/s**, PIC16 in 10.5 s = **19 M cycles/s**. |
| P2 | M | T | A reset that is not a power-on reset costs about **0.4 ms** on a PIC18: 20 000 `RESET` instructions take 8.1 s on the Q10 and 8.3 s on the Q41, against 0.014 s on a PIC16F15244. `Pic18::reset_cond` rebuilds every peripheral with `Periph::bind`, which makes several hundred `format!` + `Device::find_sfr` calls (a linear search of the SFR list), and parses the stimulus TOML again. Stack traces of a slow run were all inside `bind`. A program in a reset loop (stack underflow, watchdog) runs about 100 times slower; this is what the fuzzer's time-outs were. A name-to-address map in `Device`, or binding once and resetting state, removes it. **Fixed** (`877b34e` and this change): a warm reset clones a peripheral set bound once per stimulus, and decodes the configuration words in place without allocating (`Config::redecode`) and only once. 20 000 `RESET`s now take 0.069 s on the Q10 and 0.068 s on the 18F05Q41 (about **3.4 µs** each, 120 times faster). The first `bind` after a load or a stimulus change still costs about 1.3 ms. |
| P3 | L | R | The stimulus is searched linearly: `port_levels` walks the whole `drive` list on every `PORTx` read and every PPS pin lookup, `next_drive`, `ioc_scan`, `clc_scan`, `clock_edges` and `gate_plan` filter it again per call, and `pin_feed`/`analog_feed` re-sort the list after each entry. A stimulus with thousands of edges (a clock on `T0CKI`) makes every instruction proportionally slower. **Fixed**: `drive.rs` keeps the pin changes sorted (inserted in place, equal cycles in the order given) with each port's driven level after every change, so `port_levels` is a binary search and every time-window query (`ioc_scan`, `clc_scan`, CCP capture, clock edges, gate plans, `next_drive`, the PIC16 equivalents) takes only the changes in its window; the analog list is inserted in place and searched the same way. 20 000 edges on `RA0`, single-stepping 1 M cycles with a `PORTA` read each step: 118 s before, 0.61 s after (0.39 s with no edges); loading the edges 91 ms -> 1.7 ms. |
| P5 | L | R | With LEDs or an OLED on the board, `board_poll` runs after every instruction: it rebuilds the wiring check for each hardware-bus OLED (a formatted error string per instruction while the PPS set-up does not match) and allocates the `forced` vector. An LED keeps at most 20 000 changes and drops the oldest with `Vec::remove(0)` (`board.rs:637`), a 20 000-element move for every change once a PWM-driven LED has filled it; the "N changes" that `basil-sim` prints stops at 20 000. **Fixed**: an LED keeps its last 20 000 changes in a `VecDeque` (dropping the oldest is O(1)) and counts every change in `total_changes`, which the CLI prints; each hardware-bus OLED caches its wiring check against the values it reads (bus, pins, the two input selections, the two pins' RxyPPS), so the check and its message are rebuilt only when one of them changes; `forced` is refilled in place and the per-poll `hw` vector is gone (both cores). |
| P6 | L | R | A PIC16 in Sleep without a watchdog advances one cycle per `step`, each with an interrupt-on-change scan and a board poll (`pic16.rs:2702-2711`); only a counting watchdog lets it jump. A wake-up pin edge a second away costs millions of steps. **Fixed**: a Sleep step jumps to the earliest of the watchdog time-out (when it counts), the next stimulus pin change and the end of a data EEPROM write, with or without a watchdog. Nothing else moves while Fosc/4 is stopped: the PIC16 core has no comparator model, and Timer0/Timer1 count in Sleep only on their clock pins, which are stimulus edges. A UART still receiving is stepped cycle by cycle as before. A Sleep waiting for an IOC edge 10 M cycles away: 9 999 999 steps before, under 10 after (`pic16_ioc.rs`). |
| P4 | L | R | The logs `tx`, `spi_tx`, `i2c_log` and `pin_log` grow without limit (`periph.rs:442-493`; only `sig_log` is pruned). A PWM output adds two `pin_log` entries per period, so a long run in the window keeps allocating. Sleep with an interrupt enabled but no timer or pin event pending advances one cycle per step (`pic18.rs:855`). |

## Improvements

Ordered by what they would give a user. Items the manual already lists as limits are marked (doc).

**Fidelity**

1. The clock. Fosc is one number from the stimulus file or the window; `OSCCON1`, `OSCFRQ` and `OSCTUNE` written by the
   program change nothing (doc). Deriving Fosc from the oscillator registers would make the watchdog, LFINTOSC timers,
   baud rates in real units and the *Time* readout right without the user repeating the program's setting.
2. The Q41 has no watchdog, CCP, PWM, CWG, comparator, CLC, CRC, INTx or interrupt-on-change model (doc); `bind` gates
   all of them on `ADCPCON` being absent (`periph.rs:622`). A Q41 program with `WDTE` on gets only the note "a timeout
   reset is not modelled".
3. PIC16: the PWM modules, the 180x6 ADC and CCP, the EUSART pins, and peripheral-to-pin loopback are missing (doc).
4. Weak pull-ups and open-drain outputs (doc). Without pull-ups every button input needs a stimulus entry.
5. `XINST` (B5): either model the extended set or say at load time that the configuration asks for it.

**Stimulus**

6. Periodic sources: a clock or square wave (`period`, `duty`, `count`) instead of one entry per edge.
7. `at` is limited to 2^32 cycles (`stimulus.rs`, `MAX_CYCLES`), 268 s at 64 MHz. Times in seconds or milliseconds
   beside cycles would be easier to write and independent of Fosc.
8. Stimulus that reacts to the program (a UART echo, an I2C sensor with registers) rather than fixed byte lists.

**Window**

9. A terminal pane for UART output and input; today the transmit log is visible only in `basil-sim`.
10. Change a register, a memory cell or a pin level from the window (doc: "not a hardware debugger"). A click on a pin
    to toggle an input is the smallest useful step.
11. A waveform view of `pin_log` and the LEDs; data breakpoints (stop on write to an address); a list of breakpoints;
    keyboard shortcuts for Run, Step and Line.
12. In the disassembly, *follow PC* puts the PC on the first line; a few instructions of context above it would help.
13. `--devices` for `pic-sim`, and a session file (program, part, stimulus, watches, board).

**Command line**

14. `--help`; `--dump` with numeric addresses and ranges; machine-readable output (`--json`) for test scripts;
    `--trace` with a chosen register list and by PC range or symbol, not only by cycle range; a VCD export of the pins.
15. `--config` for PIC16 parts (refused today).

**Code**

16. Replace the `u8` hook codes with an enum (B1/B2).
17. Share the timer, port and stimulus code between `periph.rs` and `pic16.rs`; the two cores each carry their own
    Timer0/1/2, ports, IOC and PPS, and a fix in one (B4) has to be remembered in the other.
18. Split `periph.rs` (2557 lines) and `pic16.rs` (3194 lines) by peripheral, as `periph/` already does for the rest.
19. Family differences by a field in the device description rather than `name.starts_with(...)` in six places (B3).

## Smaller observations

Seen while reading and not raised to a numbered finding. All by reading (R).

* `Pic16::read` and `Pic16::write` (`pic16.rs:1705-1712`) are public and index data memory with the address as given; an
  address of 2000h or more panics. `Pic16::peek` masks the address. Only tests and tools call them.
* `Machine16::load_hex` adds to the stored image (`machine16.rs:36`), `Machine::load_hex` replaces it (`machine.rs:57`):
  loading a second hex into the same machine behaves differently on the two families.
* A PIC18 write to `PORTx` stores the value in `LATx` masked with `PORTx`'s implemented bits, not `LATx`'s
  (`periph.rs:2185-2189`); the PIC16 core masks with `LATx`'s (`pic16.rs:1045`).
* The transmit log holds eight bits per character (`periph.rs:442`, `uart.rs`, `quart.rs`): the ninth bit of a 9-bit
  or address-mode character is not recorded or shown.
* After a warm reset on a PIC18 the new Timer1 objects start with `last = 0`, so the first gate plan covers the whole
  run so far (`periph.rs:1705-1706`); interrupt-on-change has `ioc_rebase` for exactly this and the gate has not. Whether a
  stale `TMRxGIF` can result was not tested: after a reset the pins are analogue again and read 0, which hides it.
* The program counter wraps at the size of the part's flash (`pic16.rs:2583-2590`, `pc_mask` in `pic18.rs:236`), not
  at the width of the PC, so running past the end of the program continues at address 0 instead of through unimplemented memory.
* `tests/sim/run.sh` holds the only end-to-end tests of `basil-sim` with stimulus files. It needs the `basil` compiler
  from another repository and is not part of `cargo test`, so a clone cannot run them.
* `DebugInfo::rom_bytes` adds an offset to a `u32` address without a wrap (`debuginfo.rs:350-353`); a Watch on a constant
  near FFFFFFFFh would overflow in a debug build.

## Limits of this review

* Reading finds what is inconsistent or unsafe in the code. It does not prove the timing of a model against a part: the
  instruction semantics and every peripheral rule were read against the comments that cite the data sheets, and only
  B5 was looked up in the data sheet itself (DS40002043F 38.2 p.681, DS40002214G 45.1 p.807). One suspected fault was
  dropped that way: the Q41 UART ignores `UxBRG` writes while `ON` = 1, which is what DS40002214G 34.20.8 note 2 (p.558) says.
* The fuzzers found no crash or overflow in the PIC16 core, the ELF reader or any peripheral other than B1 and B4; they
  ran random and corrupted programs, not stimulus files.
* The window was read, not run: nothing in the G table was confirmed by clicking.
* The device files were not re-audited against the data sheets (see `REVIEW-FINDINGS.md`).
